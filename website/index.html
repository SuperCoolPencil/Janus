Chapter one of five · we have a disk, but no map

What is a filesystem,
really?

Imagine being handed a brand-new disk. It is not empty in the friendly, folder-shaped way your computer makes it look; it is simply a vast row of places where bytes can be written and later read back. A filesystem is the set of conventions that turns that unhelpful blank expanse into a place where names, folders, dates, and files can exist. It answers questions such as “what does this name refer to?” and “which bytes should I return when someone opens this file?”

We are going to become ext4 readers. We will not invent these conventions or guess at them; we will carefully read the structures that Linux wrote onto the disk and see how a filesystem can translate those answers into the language Windows expects.

▦

The disk

Physical storage: a long, numbered sequence of sectors holding nothing but bytes.

◫

The partition

A bounded region of the disk that can hold one filesystem, such as an ext4 volume.

✦

The filesystem

The catalog and rules that explain how this region is organized and how its bytes relate.

⌁

The file

A name that starts a trail through that catalog until the file’s contents are found.

What we discovered

The disk stores bytes, while the filesystem stores the meaning that connects those bytes. We know our ext4 partition contains a map, but we still need a dependable place to begin reading it.

Chapter two of five · find the first trustworthy clue

Where does ext4 begin?

We cannot search the disk for a filename because we do not yet know which bytes represent names. What we need is one address whose meaning is fixed in advance. ext4 gives us exactly that at byte 1024, where the superblock begins and tells us how the rest of the filesystem is organized.

First clue · the filesystem’s identity card

The superblock tells us how to read everything else.

At exactly byte 1024 from the beginning of an ext4 filesystem lives its superblock. This is the one fixed landmark we can trust before we know anything else. It records the filesystem’s block size, how many inodes and blocks exist, how many blocks belong in a group, and how large each group descriptor is. We read it in ext4/superblock.go, check the ext4 magic number, and derive the geometry we will need for every later calculation.

Chapter three of five · learn how one clue points to another

Four structures stand between our path and its bytes.

We can now read the filesystem’s opening page. The next challenge is understanding the chain of references it reveals, because every answer gives us the address needed to ask the next question.

Peel one · superblock

The first 1024 bytes are quiet. Then the filesystem introduces itself.

The superblock is not a list of every file. It is much more useful than that: it is the legend for the whole map. A value named S_log_block_size tells us the size of an ext4 block using 1024 << value; another says how many inodes live in each group; another tells it whether the filesystem was cleanly unmounted. Without this information, an offset such as “block 812” would have no meaning at all.

We deliberately refuse an unclean filesystem because ext4 may need journal recovery after an interrupted write, and this reader does not replay that journal. The project chooses safety over pretending that partially recovered data is straightforward.

Peel two · block groups and the GDT

One enormous filesystem is divided into neighborhoods.

Rather than keeping every inode and every allocation record in one gigantic structure, ext4 divides the partition into block groups. Each group is a local neighborhood with bookkeeping for its own blocks and inodes. After the superblock comes the group descriptor table, often shortened to GDT: one descriptor for each neighborhood.

A group descriptor tells us where that group’s inode table begins, along with its block bitmap and inode bitmap. In ext4/group_descr.go, we load those descriptors after it has learned the block size and descriptor size from the superblock. This is the moment the abstract filesystem map starts gaining addresses.

Peel three · inode tables

An inode is a file’s record, not its name.

This is usually the moment filesystem design starts to feel clever. A directory is a list of names paired with inode numbers; the inode table is where those numbered records live. When we see the name hello.txt in a directory, we read that entry’s inode number, determine which group owns it, find that group’s inode table through the GDT, and calculate the exact byte offset of the record.

The inode describes whether the thing is a regular file, directory, or symbolic link; it includes the size, timestamps, permissions, and the data mapping. This separation is why renaming a file is mostly changing a directory entry rather than moving its contents.

Peel four · data blocks and extents

Eventually, the map points to the bytes you came for.

For modern ext4 files, the inode usually contains an extent tree. An extent is a wonderfully compact promise: a run of logical blocks in the file belongs to a run of physical blocks on disk. Small files can keep that map directly inside the inode; larger or fragmented files can point to more nodes on disk. We walk this tree in ext4/extent.go and use the result in ext4/file.go to satisfy reads at a requested file offset.

Directories work this way too. Their data blocks contain directory entries, names and inode numbers, which gives us the next clue while walking a path like /home/ada/hello.txt.

We have all four clues

We know what every structure means, but understanding the nouns is not the same as performing the read. It is time to calculate actual offsets and watch raw bytes turn into useful information.

⌁

The final design decision

We can read the story without rewriting it.

All of this careful navigation is intentionally one-way. Operations that would write, create, delete, rename, or change metadata return EROFS, the standard “read-only filesystem” answer. That is what makes this a reassuring way to explore a Linux partition from Windows: we are here to understand, not to alter.
